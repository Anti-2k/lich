# Mixins

When the [events](events-and-hooks.md) don't expose what you need, change the game with a Mixin. Lich runs **Mixin
0.8.7** (Fabric's fork, `0.17.3+mixin.0.8.7`) and **MixinExtras 0.5.0** for Lich mods, on SRG names, in both the
Forge and the plain profile. If you know Mixin from Fabric, this is the same Mixin; this page covers what is specific
to Lich.

Lich starts this Mixin only when at least one Lich mod is installed. Your Mixins and Lich's own hook Mixins are
registered together, Lich's hooks first.

## The pieces

A Mixin in a Lich mod needs three things:

1. a **Mixin config** JSON in your jar, listed under `"mixins"` in `lich.mod.json`;
2. the **Mixin classes** in the package that config names;
3. a **refmap**, generated by the build, that translates the MCP names in your annotations into SRG names.

### 1. The config

`src/main/resources/mixins.hello.json`:

```json
{
  "required": true,
  "minVersion": "0.8",
  "package": "dev.example.hello.mixin",
  "refmap": "mixins.hello.refmap.json",
  "compatibilityLevel": "JAVA_25",
  "mixins": [
    "MinecraftMixin"
  ]
}
```

| Key | Notes |
|---|---|
| `required` | `true`: a Mixin that fails to apply stops the launch. Use it so a broken mod does not half-work |
| `minVersion` | `"0.8"` |
| `package` | Where the Mixin classes are. Names in `mixins` are relative to it |
| `refmap` | The refmap file's name, **exactly** the name you give `mixinRefmap(...)` in Gradle |
| `compatibilityLevel` | `"JAVA_25"` (what Lich's own Mixins use). Mod classes are Java 25 |
| `mixins` | The Mixin classes, relative to `package` |

Then in `lich.mod.json`:

```json
"mixins": ["mixins.hello.json"]
```

And in `build.gradle.kts`:

```kotlin
lich {
    minecraft("1.8.9")
    mixinRefmap("mixins.hello.refmap.json")
}
```

`mixinRefmap` does the work of a Mixin annotation-processor setup: it adds Mixin, MixinExtras and the ASM modules it
needs to the processor path of that source set, passes it the MCP→SRG mapping, and writes the refmap into the
compile output. It also has the processor write a mapping file (`-AoutSrgFile`) that `reobfJar` takes as an extra
mapping when it renames the jar.

### 2. The Mixin

```java
package dev.example.hello.mixin;

@Mixin(Minecraft.class)
public abstract class MinecraftMixin {
    @Shadow
    public int displayWidth;

    @Inject(method = "startGame", at = @At("RETURN"))
    private void hello$started(CallbackInfo ci) {
        LogManager.getLogger("hello").info("Game started, display width {}", displayWidth);
    }
}
```

Write the annotation arguments (`method = "startGame"`, `target = "Lnet/minecraft/...;..."`) with **MCP names**, the
names you see in your IDE. The processor checks them against the compile classpath, so a typo or a wrong descriptor is a
**compile error**, not a game crash. The refmap carries the SRG equivalents to the running game.

MixinExtras is on the compile classpath, so `@WrapOperation`, `@ModifyExpressionValue`, `@Local`, `@Share` and the
rest are available. Lich's own hooks use it (see `ChatMixin` in `versions/1.8.9/api` for `@WrapOperation`).

Two things to know when a Mixin targets a Forge class on **1.12.2**. Forge's own packages are signed in the recommended
build (14.23.5.2859) and in 14.23.5.2860, and every class of a signed package must carry the same signatures, while a class Mixin creates
(javac's switch map for a `switch` on an enum, an anonymous inner class) has none: it fails with `SecurityException:
signer information does not match`. Keep such constructs out of a Mixin whose target is a Forge class (use `if`
chains, not `switch` on an enum). The same Mixin works in the latest build (14.23.5.2864), which Forge ships unsigned,
so only the signed builds show the failure.

### 3. The refmap

Produced by the compile, bundled into the jar. In a single-version build you do not touch it. `reobfJar` then
renames the **rest of the jar's code** (your normal classes) from MCP to SRG, so the jar you ship is consistent:
code in SRG, refmap in SRG.

Check a built jar:

```
jar tf build/libs/lich-hello-1.0.0.jar | findstr refmap
```

If the refmap is not in the jar, the Mixin config's `"refmap"` name and the Gradle `mixinRefmap(...)` argument do not
match, or no Mixin annotation was found in that source set.

## Rules and pitfalls

- **Never reference a Mixin class from other code.** Mixin classes are templates, loaded and merged by Mixin; loading
  one directly throws `IllegalClassLoadError`. Put shared helpers in an ordinary class, and have the Mixin call it.
- **Name your injector methods with a prefix** (`hello$started`), and mark added fields and methods `@Unique`,
  so they cannot clash with other mods' Mixins that target the same class.
- **Lich's hooks are already woven** when your Mixin applies. If you inject into the same method as a hook you listed,
  the order between them is Mixin's priority rules. Prefer the event.
- **Forge changes some game classes**: Forge's binpatches, FML's transformers and coremods all run before Mixin. In
  the Forge profile the class your Mixin targets is Forge's version of it. Test both profiles ([Forge and Lich](forge-interop.md)).
- **Forge mods' own Mixins** (shaded Mixin 0.7, UniMixins, ...) are separate from this one and run on the copy those
  mods ship. They do not see your config and you do not see theirs, but both end up transforming the same classes.
- **Shared code cannot hold Mixins in a multi-version jar.** Refmaps are per version. Put each version's Mixins in its
  own source set ([multi-version](multi-version.md)).
- **Access wideners run after Mixin** (they are among Lich's last transformers). A Mixin therefore sees the
  game's original access flags; `@Shadow` works on private members as usual. The widener matters for your
  *ordinary* code that touches the member directly.

## Debugging

- A Mixin that fails to apply is reported by Mixin in the game log during startup, naming the Mixin class and its
  target. With `"required": true` the game stops there.
- Mixin's usual diagnostics should apply, for example `-Dmixin.debug.export=true` to dump the woven classes. That is a
  Mixin property, not a Lich one, and Lich's docs have not been checked against it. Pass JVM arguments through
  your launcher, or with devlaunch `-Plich.args=--jvm-arg -Dmixin.debug.export=true`.
- To find out whether you need a Mixin at all, check [Events and hooks](events-and-hooks.md) first.
